# Group C: verification patterns from seven past hackathon projects

Researched 2026-11-20 for the household-agent team (SingleStore, Airbyte, Amplitude + Statsig, Firedrill, maybe Superlinked SIE and Senso).
Method: project details from each cerebralvalley.ai gallery page's JSON-LD block; repo READMEs, file trees, dependency files and grep of source via the `gh` API. Nothing was cloned, installed or run. Awards are as stated on the gallery page (the `award` field).
"Verified in code" = seen in a dependency file or source. "Claimed" = only on the gallery page or README.

## 1. Labbit (AIE Code Summit 2026 Hackathon, Nov 7-8 2026)

- **What it is:** A browser robotic-hand workbench and a reproducible dataset factory for MuJoCo hand / tabletop manipulation episodes (goal: 100,000 20-second episodes). An LLM proposes bounded physics parameters; MuJoCo does the physics; a vision model reviews some episodes.
- **Award:** 1st Place (gallery page JSON-LD). Web search (2026-11-20): not found (query "AIE Code Summit 2026 hackathon winners" returned no results for this event).
- **Repo:** https://github.com/nayeonshin/aie-code-summit-2026-hackathon (public). Live: https://labbit.science. Dataset: Hugging Face `MedSalim/labbit-robotic-manipulation`.
- **Stack, verified in code:** React 19 + Three.js + Vite front end; `@mujoco/mujoco` (WASM) in a browser worker; Python FastAPI + `mujoco` + numpy + pyarrow (Parquet) back end; Cloudflare Worker + R2 storage (wrangler); Playwright + pytest tests. Models called over HTTP: Meta `muse-wonder-1.0` via `api.meta.ai/v1/responses` (parameter plans), `muse-spark-1.3` mentioned, and SubQ `subq-snap-1.1` via `api.subq.ai/v1/systemone` (image+text review of rendered frames). No database beyond R2 objects + JSON manifests.
- **Architecture:** Objective + coverage quota (config/objectives.json, quotas sum to 100%) -> seeded bounded parameters, optionally proposed by Muse -> MuJoCo physics ("never an LLM pretending to be physics") -> numerical validity checks + tracking scores -> selective SubQ visual review -> versioned shards + manifest with SHA-256 per shard -> replay. Improvement is not a learning loop; quality is measured as "N episodes numerically valid / passing the tracking proxy / quotas met".
- **How results are presented:** Dense honest tables: 390 episodes / 148,500 frames, all passing validity checks; 100 x 20 s episodes in 9.47 s; compact format 132.7 MB vs 1,077.1 MB (88% smaller). Heavy use of explicit non-claims ("assisted grasps, not a learned policy", "36 rigid particles, not water", a shown push episode "finishes 24.7 cm from its target - a retained failure, not a success claim"). Planned vs recorded vs reviewed counts kept separate; unreviewed items labelled "SubQ not reviewed" rather than fabricated.
- **Borrow:**
  1. **Separate "proposed", "executed", "reviewed" states and never blur them** -> in SingleStore, an `order_proposals` row is distinct from an `orders_placed` row and from an `approvals` row; the ledger UI shows which stage each item reached. Labbit's "Muse proposal is not a demonstration" maps to "LLM shopping suggestion is not an approved order".
  2. **Paid/irreversible actions need an explicit cap and token** (Labbit gates Muse/SubQ calls behind an admin token and a spending cap) -> gate the test-mode order behind a per-household budget cap checked in code, and log the cap check result as evidence. Statsig can hold the cap value as a dynamic config.
  3. **Content hashes on evidence** (SHA-256 per shard, pinned dataset revision) -> store a hash of each receipt / calendar snapshot used for a decision, so a ledger entry points at immutable evidence (fits Senso's versioned citations if used).

## 2. Frankenstein (AIE Code Summit 2026 Hackathon, Nov 7-8 2026)

- **What it is:** Agents rebuild lost source code of a compiled game (GBADoom) one function at a time; a compiler-based referee accepts a function only if it compiles to byte-identical machine code. The relinked ROM has the same SHA-1 as the original.
- **Award:** 3rd Place (gallery page JSON-LD). Web search (2026-11-20): not found.
- **Repo:** https://github.com/KarthikSubramanian07/Frankenstein (public, MIT; `lab/out/` GPL). Live: https://tryfrankenstein.pages.dev.
- **Stack, verified in code:** Mostly Python; `crew/requirements.txt` = python-dotenv + `pymongo` (MongoDB Atlas "habit library", optional, no-op without `MONGODB_URI`); jsonschema + pytest for contract tests; `crew/config.py` references Muse Spark, `crew/gemini.py` for the Gemini second-opinion reviewer; Node packages for the Stage (live replay UI) and phone page; Cloudflare Pages for the site; devkitARM in Docker for the referee; mGBA emulator. SubQ Snap routing and Fetch.ai ASI:One/Agentverse agents: not found by code search in source files; README/docs only.
- **Architecture:** Lab splits the ROM into 568 anonymous functions; the real source is a hidden answer key only the referee reads. Digger agents (Muse Spark, escalating to Muse Wonder) write C -> referee compiles and byte-compares, returning the first differing instruction on rejection -> a separate Checker re-runs every "I matched it" claim with a fresh compile and lints for cheats (inline asm, hard-coded addresses) -> Gemini second opinion -> accepted functions relinked, whole-ROM SHA-1 must match. SubQ Snap decides which function to try next and when to escalate. Lanes communicate only via JSON-schema contracts and an append-only `runs/<run_id>/events.jsonl`; the Stage UI is driven only by that event stream. Improvement measured with frozen train/held-out splits, pinned git worktrees per arm, and a $ budget per run (`crew/EXPERIMENTS.md`).
- **How results are presented:** A results table where every row cites its source file (235/568 functions, 41.4%; SHA-1 identical; 39 false claims caught, 32 fake matches rejected, 0 accepted). An anti-memorization probe (0/20 from memory; 0/4 on secretly modified functions). Crucially, a negative result stated plainly: habit library on vs off = 29 vs 29 / 6 vs 6, "No measured gain, so we don't claim one." Plus a memorable demo proof: edit one recovered line to give 200% health. UI convention: bright = compiler-proved, violet "?" = guess ("Observed" vs "Inferred").
- **Borrow:**
  1. **Count caught false claims as a headline metric** -> when the agent claims "milk runs out Thursday" or "Alex approved", a code checker re-derives it from SingleStore receipts/approval rows; log `claims_made / claims_rejected` as Amplitude events. "0 fake approvals accepted" is a strong demo line.
  2. **Observed vs Inferred labels on every ledger entry** -> each ledger field tagged as observed (from an Airbyte-synced receipt/calendar row, with row id) or inferred (model forecast); Senso citations can back the "observed" side.
  3. **Append-only event log as the single source for the UI and the metrics** -> one SingleStore `agent_events` table that the ledger view, Amplitude export and replay all read; and an honest A/B (Statsig) with a frozen held-out set where a null result is reported, not hidden.

## 3. Etch (The Recursive Agents Hackathon, Crusoe, Oct 17-18 2026)

- **What it is:** One spoken/typed sentence ("build a GPS tracker like an AirTag") -> agents pick real parts, write a board spec, place and route in KiCad, and must prove the board works before saying "done". Exports Gerbers/BOM and a 3D model.
- **Award:** 1st Place (gallery page); the repo description also says "1st overall, Recursive Agents Hackathon ($14K)". Web search (2026-11-20): not found (no official winners list surfaced).
- **Repo:** https://github.com/PranavAchar01/etch (public). Live: https://etch.chat.
- **Stack, verified in code:** Python (uv; `engine/pyproject.toml`: pyyaml, pygltflib, numpy; agent runs with `openai` SDK against an OpenAI-compatible endpoint). `agent/config.py`: default base URL `api.inference.crusoecloud.com/v1`, lead model `nvidia/NVIDIA-Nemotron-3-Super-120B-A12B`, sub-agent `nvidia/Nemotron-3.5-Lightning-30B-A3B`, OpenAI fallback, `ETCH_MAX_ITERS` default 4 (README body says "up to three tries"; config and gallery say 4). KiCad 10, ngspice, easyeda2kicad, cloudflared tunnel, static front end on Vercel (Three.js viewer), local Parakeet speech-to-text (sherpa-onnx). A small local part-category classifier (`agent/classifier.py`: e5-small ONNX embeddings + logistic regression trained on KiCad footprint libraries). Claimed on page but not checked in code: NVIDIA prompt-complexity classifier for routing (a `task_router.py` exists), You.com search (`YOU_API_KEY` is read per README).
- **Architecture:** Lead agent + sub-agents (spec writer, feature writer, part scout) via Chat Completions tool calling -> plain code builds (place/route) -> gate runs ERC, DRC, schematic-to-PCB parity, unconnected nets, 3D models, ngspice simulation, and request-specific benchmarks -> failures go back to the picker as a repair, up to 4 iterations, then stop and say why. `agent/live_bench.py`: "A model only MAPS each spoken requirement onto one of the checks below and its limit. Every value is then measured by plain code ... A requirement that maps onto no check is reported as 'cannot measure', never guessed." `agent/watchdog.py`: per-stage silence caps (set above the longest real silence seen in 164 prod runs) and a 13-minute run cap; on trip it emits an honest timeout message and `done ok=False`. Every part carries provenance (source URL, commit/version, licence, STEP sha256); no file -> `not_found`. Output is one JSON event per line.
- **How results are presented:** Demo-first: GIFs of a sentence becoming a routed board, 3D orbit, export, a library of 135 real open-source boards credited to authors. Persuasion comes from the "nothing is invented" stance (real files with hashes, "cannot measure", "not found", honest timeouts) more than from a single before/after number.
- **Borrow:**
  1. **Checks defined before the run; the model only maps requirements to checks; code measures; unmappable = "cannot measure"** -> for an event ("Saturday BBQ for 8"), the planner turns needs into named checks (`servings >= 8`, `budget <= $60`, `no item already in stock`, `approver is the person who owns that budget`) stored in SingleStore before ordering; code evaluates each against receipts/inventory; anything it cannot evaluate is shown as "cannot measure" in the ledger, never as passed.
  2. **Watchdog with honest failure** -> per-step time caps on the Airbyte sync, approval wait and order call; a timeout writes `done ok=false, reason=timeout:<step>` to the ledger and fires an Amplitude event, rather than silently retrying or faking success. Good Firedrill scenario: "approver never replies".
  3. **Small local classifier for a narrow sub-task** (e5-small + logistic regression for part category) -> a Superlinked SIE-style small model to classify receipt line items into supply categories (paper towels, dish soap), with its accuracy measured and shown, instead of an LLM call per line.

## 4. SPARKLETEAM / RSHI (The Recursive Agents Hackathon, Crusoe, Oct 17-18 2026)

- **What it is:** "Recursive Self Home Improvement": a team of five Nemotron models plays a physically simulated dishwasher-loading game (DishwasherBench by composo-ai, MIT, used unmodified as a submodule), rewrites its own prompts/playbook/tools/team structure, and keeps an edit only if it wins a paired, measured test. Headline: it learned one real law of physics and one superstition, and they measured which was which.
- **Award:** 2nd Place (gallery page JSON-LD). Web search (2026-11-20): not found.
- **Repo:** https://github.com/elevenarms/RSHI (public). Project page https://elevenarms.github.io/RSHI/, paper PDF and run logs (`crew/runs/`, ~737 files) in repo.
- **Stack, verified in code:** TypeScript pnpm monorepo. `crew/src/crusoe.ts`: Crusoe Managed Inference (`api.inference.crusoecloud.com/v1`) with per-role models - loader `Nemotron-3.5-Lightning-30B-A3B` (deliberately the weakest competent model), planner `Nemotron-3.5-Super-VL`, critic `Nemotron-3-Nano-Omni-Reasoning-30B-A3B`, coach `Nemotron-3-Super-120B-A12B`, librarian `Nemotron-3-Nano-30B-A3B`; client-side rate limiter (25 RPM). Simulation/scoring from DishwasherBench workspace packages (`@spotless/*`). Studio = Vite visualizer with SSE. Memory is plain files (JSONL), no database. Also `sft.ts` (fine-tuning data export, described as "next recursion").
- **Architecture:** Typed self-edits proposed by coach/planner/critic -> candidate genome vs incumbent play the same fresh validation tasks -> `gatekeeper.ts`: paired comparison, keep only if mean score beats incumbent by a margin (default 0.03) AND fails no more episodes; infrastructure failures excluded from both sides; fewer than 3 valid pairs = void decision. Three-layer memory (`crew/src/memory`): episodic (`episodes.jsonl`; exam episodes kept apart and never learned from), semantic lessons with Beta(1,1) confidence `p=(s+1)/(n+2)` from supporting/contradicting episodes, procedural (genomes + gatekeeper `decisions.jsonl` -> champion). Improvement measured on a held-out exam.
- **How results are presented:** A crisp physical finding with counts (cup mouth-up 0/11 clean vs mouth-down 26/26). Then self-critique as the hook: a 4-drill exam showed +17.8 pp, a 12-drill replication (23 pairs) showed -0.3 pp (95% CI -13 to +12) - the "superstition" was caught and explained (one rule rested on one failure in two loads; loader noise swamped the gate margin). Paper, slides, video, replayable token-level logs, and a provenance table separating hackathon work from upstream.
- **Borrow:**
  1. **Beta-posterior confidence on each learned "lesson"** -> each consumption belief ("household uses 1 roll of paper towels per 4 days") stored in SingleStore with supporting/contradicting receipt counts and `p=(s+1)/(n+2)`; the ledger shows the confidence and the receipts behind it, so a belief from one data point is visibly weak.
  2. **Exam data never feeds learning** -> keep a held-out set of Firedrill households/scenarios that the agent's prompt tweaks are never tuned on; report improvement only on those.
  3. **Replicate before you claim** -> if a Statsig experiment shows a prompt variant wins, rerun with more Firedrill seeds and report the CI; presenting "we caught our own false win" is persuasive to judges.

## 5. AGI Factory / factory-autopilot (The Recursive Agents Hackathon, Crusoe, Oct 17-18 2026)

- **What it is:** A robot-maintenance agent team over a six-month synthetic digital twin of a real plant-room scan (14.2M-splat). The team rewrites its own playbook, tools and roles, and keeps a change only when a paired gate on unseen runs proves it scores higher without making robot work less safe.
- **Award:** 3rd Place (gallery page JSON-LD). Web search: no official list found; a search snippet from a LinkedIn post (author/URL not verified) claims a project called "Factory N+1" won NVIDIA's "Best Use of Nemotron" at this hackathon - plausibly this project (README title is "Factory Autopilot - Version N+1"), treat as unverified.
- **Repo:** https://github.com/ToukoUrsin/factory-autopilot (public).
- **Stack, verified in code:** Pure Python standard library (no requirements file; `engine.py` imports only dataclasses/random/statistics; `crusoe.py` uses `urllib`; `server.py` uses `http.server`). Crusoe Managed Inference: planner/reviewer `nvidia/NVIDIA-Nemotron-3-Super-120B-A12B`, vision `nvidia/NVIDIA-Nemotron-3.5-Super-VL`, robot pilot `nvidia/Nemotron-3.5-Lightning-30B-A3B`. Front end: vanilla JS + vendored three.js and PlayCanvas/SuperSplat viewer. Unit tests in GitHub Actions. No database; evidence is checked-in JSON (`factory/evidence/`).
- **Architecture:** Training seeds 11-18 -> deterministic failure audit -> Nemotron planner proposes from a *whitelist* of candidate edits -> paired gate on unseen seeds 101-112 (mean gain >= 1, wins > losses, unsafe actions cannot increase), with common random numbers so candidate and parent face identical incidents -> keep or reject -> leave-one-out ablation prunes edits that do not help -> one-time exam on seeds 201-212 -> Nemotron reviewer writes commentary only. "The gate is the evaluator of record: model calls can order the whitelisted edits, but cannot score or approve them." In the sim, an independent checker can block a robot's unsafe plan before execution (logged as `blocked` vs `unsafe`).
- **How results are presented:** One before/after table on the held-out exam: score 66.5 -> 92.8, unsafe actions 21 -> 0, overdue work orders 25 -> 0, evidence gaps 46 -> 15, stockouts 18 -> 8. Per-edit gate verdicts with win/loss counts (`verifier_role` +11.5, 11/0; `deadline_sweep` +12.0, 12/0; `reorder_buffer` +1.0, 9/3) and a named rejection (`fast_track` rejected because unsafe actions rose 0 -> 15). Explicit limitations, a judging-criteria map (`docs/JUDGING.md`), a 60 s scripted demo, and a checked-in negative verification record (`arm_on_site: false` -> reported as an evidence gap, not success).
- **Borrow:**
  1. **Firedrill red -> green with a safety veto** -> run simulated housemates (Firedrill) over fixed seeds; a prompt/policy change is kept only if it scores higher on held-out seeds AND adds zero "unsafe actions" (order placed without approval, over budget, wrong approver). Present the rejected shortcut (e.g. "auto-approve under $20" rejected because unapproved orders rose) - that rejection is the most persuasive slide. Statsig gates can carry the kept/rejected variants.
  2. **Model proposes from a whitelist, code scores** -> the LLM may only pick from typed edits (e.g. `reorder_buffer_days`, `ask_owner_first`, `batch_with_event`), never edit free-form logic or grade itself.
  3. **Count "evidence gaps" as a metric** -> every ledger decision without a linked receipt/calendar row counts as an evidence gap in Amplitude; drive it down and show it in the before/after table, alongside stockouts (directly analogous to their stockout metric).

## 6. LabTwin, team "polar bears" (Gemini 4 Argon SF Hackathon, Oct 25-26 2026)

- **What it is (claimed on page only):** A digital-twin "world model" for the wet lab: from a protocol (PDF/Markdown), a bench photo/video and target per-well results, Gemini 4 Argon writes a bench spec; an orchestrator fans out Antigravity Managed Agents in parallel sandboxes to write a MuJoCo whole-room scene, liquid state, reward and a Gymnasium RL environment. The twin runs the protocol step by step before a real pipette moves.
- **Award:** 1st Place (gallery page JSON-LD). Web search (2026-11-20): not found.
- **Repo:** https://github.com/benjaminxie1/argon-hacks - **returns 404 (private or deleted) as of 2026-11-20**; not under any other name in that user's public repos. Live demo https://labtwin.vercel.app returns "DEPLOYMENT_PAUSED". Video: https://youtu.be/dGreES9C6a0 (not watched). **Nothing below is verified in code.**
- **Stack (claimed):** Gemini 4 Argon, Antigravity Managed Agents, MuJoCo, Gymnasium, Vercel (hosted demo replays a cached run; live use needs a local server and API key).
- **Architecture (claimed):** Argon renders the twin from the photo's viewpoint, critiques it against the real photo and fixes itself (visual match 54 -> 88). The twin simulates each step, compares every well's volume/concentration with the target, and traces each failed well back to the exact step that caused it. "Argon, fix it" rewrites the protocol with a reason for each change, and the simulator re-runs from scratch to prove the fix. An RL agent trained from scratch on the twin reaches 1.0 success rate.
- **How results are presented:** Two numbers (visual match 54 -> 88; RL success 1.0), a live demo link up front, and an interactive "play the protocol yourself in 3D, mistakes flagged as you click". The persuasive core is the closed loop: simulate -> blame a step -> model fix with reasons -> re-simulate to prove.
- **Borrow:**
  1. **Dry-run the plan and trace a failure to the step that caused it** -> before ordering for an event, simulate the inventory timeline day by day (SingleStore rows: stock levels, forecast consumption, calendar events); if a "well" (e.g. coffee on Sunday morning) ends below target, point to the step (wrong delivery date, under-quantity) and let the model propose a fix with a stated reason; re-run the simulation to prove the fix before asking for approval.
  2. **Self-critique against the real observation** (render vs photo) -> compare the agent's predicted stock against the next real receipt (Airbyte) and log the forecast error as an Amplitude metric; show "forecast error before vs after".
  3. **Cached replay for the demo** -> keep a recorded run that replays without live keys, so the demo never depends on Gmail/OAuth working on stage.

## Cross-project patterns (what recurs across the seven)

1. **The model proposes, code verifies, and the model never grades itself.** Frankenstein (compiler byte-match referee), Etch (model maps requirements to checks; code measures from build outputs), AGI Factory ("the gate is the evaluator of record"; models choose whitelisted edits only), SPARKLETEAM (statistical Gatekeeper), Labbit (MuJoCo, "never an LLM pretending to be physics"). Household version: the LLM proposes a forecast or cart; SQL over SingleStore checks budget, stock, approver identity and evidence links.
2. **Checks fixed before the run, with explicit "unknown" states.** Etch's "cannot measure" / "not found", Labbit's "SubQ not reviewed", Frankenstein's Observed vs Inferred, AGI Factory's "evidence gap". Ledger rows should have a status like `verified | inferred | cannot_measure`, never a silent pass.
3. **One measured before/after number on held-out data.** AGI Factory 66.5 -> 92.8 and unsafe 21 -> 0 on unseen seeds (verified in repo evidence docs); Frankenstein 235/568 with SHA-1 match; SPARKLETEAM 0/11 vs 26/26. (LabTwin's visual match 54 -> 88 is a page claim and not held-out.) Train/tune on some Firedrill seeds, report on others.
4. **Paired comparison with a safety veto.** AGI Factory and SPARKLETEAM both compare candidate vs incumbent on the same scenarios (common random numbers) and reject changes that add unsafe actions or failures. Maps directly to Firedrill seeds + Statsig experiments.
5. **Reporting negative results and caught mistakes is a strength.** Frankenstein's "no measured gain, so we don't claim one", SPARKLETEAM's caught superstition (+17.8 pp -> -0.3 pp on replication), AGI Factory's rejected `fast_track`, Labbit's retained failure episode.
6. **Append-only event log + provenance for every artifact.** Frankenstein `events.jsonl`, Etch one JSON event per line with part hashes and licences, SPARKLETEAM JSONL memory + replayable token logs, Labbit SHA-256 manifests, AGI Factory checked-in evidence JSON. For the household agent: a single SingleStore `agent_events` table that drives the ledger UI, Amplitude export and demo replay.
7. **Bounded repair loops and honest stopping.** Etch (4 repair iterations, watchdog with stage caps), Frankenstein (per-run $ budget; stop at 90%), Labbit (paid calls behind token + spending cap). Cap retries for approval nudges and orders; on cap, stop and say why.
8. **Recorded/cached replay for the demo.** LabTwin (cached run on Vercel), AGI Factory (`?demo=1` scripted replay; works with no API key), Frankenstein (Stage replays a run at 1-20x), SPARKLETEAM Studio replay.

Awards come from each gallery page's JSON-LD `award` field (plus Etch's own repo description). Three brief web searches (one per hackathon) found no official winners lists; only an unverified LinkedIn snippet about "Factory N+1" winning NVIDIA's Best Use of Nemotron. Demo videos were not watched.
